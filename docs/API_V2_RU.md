# SpyderPay v0.2 — закрытый API платёжного ядра

**Не мобильный API.** В этой версии реализована исключительно авторизация «сервис ↔ сервис». Ни iOS, ни Android не получают HMAC-ключ. Перед подключением пользователей нужен отдельный OIDC/BFF слой, выпуск и отзыв пользовательских токенов, MFA, step-up-подтверждение и серверные сессии с ограничением действия.

## Подпись запроса

Проверяется: `X-Spyder-Key-Id`, `X-Spyder-Timestamp` (Unix seconds), `X-Spyder-Nonce` (20–128 символов URL-safe), `X-Spyder-Signature` (hex HMAC-SHA256), `Idempotency-Key` (12–128 символов; для операций, меняющих состояние).

Подписывается UTF-8 строка:

```text
<timestamp>\n<nonce>\n<METHOD>\n<path-and-query>\n<SHA256(raw-request-body)-hex>
```

Никакой нормализации/пересериализации JSON на промежуточном прокси. Body — исходные байты. Разница во времени не более 120 секунд. Nonce записывается в БД с уникальностью `(key_id,nonce)`; повтор запрещён. Сервисный ключ — случайные 32+ байта, а не пароль. Нужен протокол ротации ключей. Подписанные HTTP-сообщения не заменяют TLS/mTLS, лимиты gateway и контроль сети.

Роли сервисной идентичности: `ops`, `customer`, `merchant`. `tenant_id` + `subject` привязываются к ключу на сервере и не принимаются из пользовательского body. В реальном приложении `customer`/`merchant` будут сервисными полномочиями BFF, делегированными после строгой проверки действующего пользовательского токена; пока такие делегирования не реализованы.

Конфигурация сервисных ключей должна приходить из secret manager, формально:

```json
[
  {
    "key_id": "svc-partner-01",
    "secret_b64": "<base64-of-32+-random-bytes>",
    "tenant_id": "tenant-demo",
    "subject": "user-alice",
    "roles": ["customer"]
  }
]
```

Пример — **схема**, не рабочие учётные данные. Запрещено хранить `secret_b64` в репозитории, push-уведомлениях, логах или файлах мобильного приложения.

## Маршруты

| Метод | Путь | Право | Эффект |
|---|---|---|---|
| GET | `/health/live` | public liveness | Не раскрывает базу, деньги или пользователей |
| POST | `/v2/accounts` | ops | Создать изолированный UZS счёт |
| GET | `/v2/accounts/{id}` | владелец / ops | Просмотреть свой UZS счёт |
| POST | `/v2/transfers` | customer | Идемпотентный перевод между customer-счетами одного tenant |
| POST | `/v2/invoices` | merchant | Создать счёт продавца с TTL 1–60 минут |
| GET | `/v2/invoices/{id}` | merchant-владелец / ops | Проверить счёт |
| POST | `/v2/invoices/{id}/pay` | customer | Провести оплату за счёт своего баланса |
| POST | `/v2/invoices/{id}/refund` | merchant-владелец | Полный возврат при достаточном балансе |
| POST | `/v2/accounts/{id}/freeze` | ops | Заблокировать движения счёта |
| GET | `/v2/ops/reconciliation` | ops | Сверить ledger и balance cache |
| POST | `/v2/sandbox/credits` | ops + env feature gate | **Только тестовое зачисление, не реальные сумы** |

Результат операций содержит идентификатор журнала, сумму в целых **UZS**, и соответствующий статус. Не хранить фиат как floating point. SPYDER Coin не допускается в UZS-ledger. Криптография собственной цепочки и реальная конверсия находятся вне этого backend.

## Ошибки и гарантия идемпотентности

- `401`: неправильная/устаревшая подпись; `409`: повтор nonce или конфликт idempotency-key с другим телом.
- `403`: недостаточное полномочие или чужой счёт; `422`: неправильная схема/сумма/идентификатор.
- `429`: превышен базовый лимит на один сервисный ключ; дополнительно обязателен WAF/rate limiting на входном шлюзе.
- Идемпотентность: `(tenant:subject, key)` + SHA-256 тела операции в той же транзакции PostgreSQL. Повтор **с новым nonce**, но тем же idempotency-key и неизменённой операцией возвращает исходный результат.
- Outbox выполняет **at-least-once** delivery; внешний получатель событий должен принимать `event_id` и дедуплицировать. Диспетчер outbox и реальные webhooks ещё не реализованы.
- Работа в интернете и подключение к реальным финансовым сетям запрещены до завершения production gates.
