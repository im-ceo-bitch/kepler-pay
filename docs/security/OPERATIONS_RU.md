# SpyderPay Security Operations — контрольный стандарт

Это начальный runbook для службы эксплуатации. **Не подтверждение проведённой сертификации.**

## Доступ и секреты

- Изолировать production VPC и базы от публичного интернета. Единая входная точка через mTLS reverse proxy и WAF.
- Создавать отдельные сервисные аккаунты и БД-роли для API, миграций и аналитики. API не должен иметь `SUPERUSER`, `CREATEROLE`, `BYPASSRLS` или возможность менять триггеры.
- Сервисные HMAC-ключи генерировать криптографически случайно, выдавать через secret manager и регулярно ротировать. При компрометации отзывать сразу и расследовать все подписанные операции.
- Поддерживать отдельный break-glass доступ с MFA, протоколированием и обязательным разбором после использования.
- Никаких PCI PAN/CVV, seed-фраз, ключей карт и KYC-документов в ledger, логах и GitHub Actions.

## Security monitoring и реагирование

Мониторить: 401/403/409/429, spikes nonce/replay, подозрительные изменения частоты переводов, рост `lock_timeout`, отказы оплаты и возврата, задержку outbox (отдельный alert для событий с `attempts >= 25`), расхождение balance cache и postings, невыполненную сверку, секреты в CI.

При подозрении на атаку:

1. Включить incident channel, зафиксировать время и затронутые account/journal IDs, не логировать секреты.
2. Ограничить API gateway/отозвать сервисный ключ; при риске денежного ущерба заблокировать операции соответствующего контура.
3. Не делать прямых SQL UPDATE балансам для «ремонта». Использовать только формально согласованные компенсирующие проводки.
4. Сохранить DB WAL, аудит, outbox и proxy security logs для расследования и сверки с банком.
5. Запустить независимую reconciliation; определить ущерб, оповещения и обязательную отчётность по применимым требованиям.
6. Выпустить postmortem, закрыть root cause тестами и перевыпустить с процедурой approvals.

## Backup, failover и DR — будущие gate

- PostgreSQL PITR с WAL archiving, шифрованными резервными копиями, отдельным аккаунтом и разными ключами.
- Ежемесячно восстановление в изолированную среду и независимая сверка ledger; ежеквартально полноформатный recovery drill.
- Установить RPO/RTO с регулятором/партнёром; не выдавать произвольные цифры за достигнутые SLA.
- HA leader election, safe fencing, запрет split-brain и тесты недоступности банкинга/сети.
- Идемпотентность восстановленных повторных запросов, event delivery at-least-once и reconciliation должны переживать рестарт.

## Release change management

CI + code review (минимум 2 одобрения для ledger/auth/schema), запрет прямых правок production DB, отдельные staging/prod secrets, signed tags/releases, rollback runbooks. ZIP action для ускорения разработки **не должен** быть единственным путём выпуска в регулируемую инфраструктуру.
