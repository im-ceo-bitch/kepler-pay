# SpyderPay: три крупных инженерных блока

Цель: подготовить собственный платёжный процессинг к интеграционному аудиту, не принимать реальные деньги до юридического разрешения, сертификации и внешних проверок. Blockchain, mobile app и core — разные репозитории.

## Блок 1 — security, identity, ledger (v0.3)
- Вход через доверенного OIDC IdP; локальная привязка субъекта к tenant/роли, отзыв сессии.
- Раздельный серверный HMAC v3 с идентификатором ключа и подписанным ключом идемпотентности.
- Step-up challenge: инициировать, заново пройти MFA, подтвердить новым токеном, выполнить ровно ту операцию, которую подтвердили. Атомарное потребление разрешения с проводкой.
- PostgreSQL: неизменяемые реквизиты и финализированный журнал, контроль кеша баланса и фактической проводки, привязка платежа и возврата к счету.
- Ограниченные роли БД, миграции без сброса данных, HTTP boundary, журналирование, CI.
- Критерий внутреннего завершения: unit + реальные PostgreSQL/concurrency + проверка ролей + интеграция с тестовым IdP. Независимый аудит остаётся обязательным перед запуском.

## Блок 2 — Payment Processing, bank connectivity & compliance
- Жизненный цикл платежа: authorise/hold/capture/release/refund, частичный возврат, отмена, тайм-аут, неизвестный результат, reversal, disputes.
- Банковские и платёжные адаптеры: единые интерфейсы и тестовые контракты, подписи callback, durable inbox/outbox, проверки идемпотентности, sandbox certification harness.
- Settlement, clearing, банковские выписки и трёхсторонняя сверка. Раздельный учёт комиссий и обязательств.
- Merchant onboarding, antifraud, лимиты по субъекту/устройству, review, KYC/AML/sanctions hooks, роли maker/checker.
- Критерий: fault-injection, проверка неизвестного результата, автоматическая сверка, отсутствие необъяснимых расхождений; реальный API требует договоров и спецификаций.

## Блок 3 — POS/NFC, эксплуатация и release candidate
- Merchant API, Android POS, QR, аппаратная NFC-авторизация после выбора и тестов Secure Element, SDK-контракты для Spider Wallet; режимы Fiat/Crypto сохраняют разные ключи, баланс и backend.
- Высокая доступность, контроль доступа, управление ключами KMS/HSM, TLS/mTLS, WAF, телеметрия, отказоустойчивость, бэкапы, PITR, disaster recovery, инцидент-процедуры.
- Нагрузочные/chaos-тесты, проверка цепочки поставки, SBOM, dependency audit, threat model и соответствие применимым требованиям, проверка внешним аудитором.
- Критерий: независимый security assessment, восстановление и нагрузка на целевых SLO, внешняя сертификация, regulator/partner acceptance. До этого — release candidate, не коммерческий production.

Банковские API, модель хранения средств, KYC/AML-провайдер, применимость PCI и регуляторные требования нельзя выдумывать. Не обещаем замену mock на реальные операции одним переключателем без внешних испытаний.
