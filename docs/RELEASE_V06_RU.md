# SpyderPay Core 0.6.0 — надёжная банковская отправка и эксплуатационные проверки

## Релиз
Накопительное обновление 0.5.0. `spyderpay-core-update-v006.zip` устанавливается существующим постоянным GitHub Actions. Никакие workflow не включены и не изменяются. Архив сохраняет предыдущие миграции и защищённые скрипты без изменений.

## Исправления предыдущего блока
- Исправлена загрузка credential всех ролей v3, включая KYC/AML, согласия и независимое утверждение выписок. Старый v2 не получает новые роли.
- Две копии SQL-профиля runtime синхронизированы; теперь deployment и интеграционные тесты используют идентичные права.
- Проверка готовности и версия API используют единый `SCHEMA_VERSION` / `VERSION`; устранены жёстко зашитые значения.
- Пример проверяющего callback отклоняет неоднозначные заголовки, повторяющиеся JSON-поля, NaN и слишком большие тела даже при валидной подписи. Это не универсальный протокол банковского callback.

## Новый контур dispatch
Миграция 005 добавляет неизменяемую запись разрешения отправки и неизменяемую запись результата. `bank_dispatch` отделён от создателя и проверяющего банковского намерения. Перед выдачей разрешения повторно проверяются лимиты, согласие, риск и статус счёта. Разрешение выдаётся один раз в транзакции, которая переводит намерение в `submitted` и фиксирует канонический reference. Ответ не выдаётся до commit. Повтор claim возвращает конфликт; его нельзя обрабатывать как разрешение отправить деньги повторно. Сетевой вызов не является частью транзакции БД.

При сетевой ошибке, потере ответа или аварии после commit отправка может как состояться, так и не состояться. `DispatchWorker.recover` выполняет только lookup по исходному reference. Неизвестный или даже `not_dispatched` результат новой схемы не освобождает резерв сам по себе. Для расчёта или освобождения по-прежнему необходимы независимые callback и утверждённая выписка. Дополнительное наблюдение не может переоткрыть завершённую операцию. Старая ручная sandbox-отправка `/v3/bank/intents/{id}/submit` сохранена для совместимости с тестовым окружением; она не является интерфейсом для живых банков. Переход на сертифицированные адаптеры потребует выключить старый маршрут и утвердить конкретный протокол партнёра.

`DispatchWorker` — координатор для доверенного внутреннего сервиса, не мобильное приложение. Adapter обязан сохранять client reference, не выполнять скрытые ретраи, ограничивать время запроса и проверять подлинность ответа. Если банк назначает собственный идентификатор, необходимо реализовать и протестировать отдельное сопоставление. Ни одного реального банка этот релиз не подключает.

## Эксплуатация (начало блока 3)
- Запуск API отказывается работать с неверной схемой, опасной ролью владельца/суперпользователя, отсутствующими правами чтения и ключевыми правами записи. Проверяется запрет DELETE/TRUNCATE финансовых таблиц и возможность только разрешённого identity lookup. Это preflight, не исчерпывающая проверка всех привилегий и не RLS.
- Закрытый health endpoint показывает просроченные dispatch claim, исчерпанные события outbox, поздние конфликтующие и несопоставленные банковские подтверждения. Реальное внешнее оповещение и реакция на инцидент требуют настройки.

## Порядок обновления среды
1. До миграции сделать и проверить резервную копию в изолированном окружении. Не применять к реальным деньгам.
2. Запустить штатный migration tool под отдельным владельцем БД. Миграция только добавляет таблицы и триггеры; старые записи не переписываются. Схема 6 обязательна для v0.6.
3. Применить `spyderpay_core/postgres/ops/runtime_roles.sql` под администратором БД. Добавить отдельный service credential `bank_dispatch` в секретном хранилище с уникальным actor и ограниченным сроком действия.
4. Запустить API от ограниченной runtime роли. Проверить `/health/live`, подписанные `/v3/ops/ready`, `/v3/ops/health` для каждого тестового tenant. Не запускать legacy API для пользовательского доступа.

## Проверки и ограничения
Локально: 233 теста и 4 защищённых security gate; bytecode compileall. Тесты PostgreSQL добавлены, но не запускались локально: нет PostgreSQL и psycopg. CI обязан выполнить их, Bandit и pip-audit. Нагрузочные испытания, работа реального IdP, KMS/HSM, проверка восстановления, независимый аудит не подтверждены. Не заявляется production readiness.

Открытые задачи блока 2: партнёрские банковские и KYC/AML адаптеры с реальными контрактами, комиссии и бухгалтерский учёт комиссий, полный chargeback и требования конкретной сети, внешняя сверка расчётного счёта. Открытые задачи блока 3: HA/DR, мониторинг, инфраструктурная защита, POS/NFC, hardware security, эксплуатационные проверки. Переход к реальным платежам требует разрешений и отдельных проверок.
