# SpyderPay Core 0.8.0 — блок 2 / pre-license

Кумулятивный релиз от v0.6, включает также локальные разработки 0.7/0.7.1:
комиссии, полный внутренний chargeback, долговечный sandbox rail и read-only
сверку банковских выписок. Реальный банковский транспорт не включён.

## Новый блок возвратов
- POST `/v3/invoices/{invoice_id}/refund-amount`, JSON `{"amount": 2000}`,
  заголовки Authorization, Idempotency-Key и X-Spyder-Approval. Merchant OIDC.
- Для MFA challenge POST `/v3/approvals` с `operation: refund_amount`,
  `invoice_id`, `expected_amount` (исходная сумма счёта), `expected_merchant`,
  `amount` (сумма именно этого возврата). Подтверждение по существующему
  маршруту `/v3/approvals/{approval_id}/confirm`. Challenge и исполнение
  должны использовать один idempotency key. Получатель берётся из
  неизменяемого оплаченного invoice, не из тела запроса возврата.
- Операции выполняются под блокировкой invoice. Пропорциональная комиссия
  считается как разница накопленных целочисленных долей: `floor(F*(R+A)/G) -
  floor(F*R/G)`. Последний возврат возвращает оставшуюся комиссию. Списание,
  комиссия, журнал, событие и погашение MFA атомарны. Не создаются деньги
  при нехватке средств. Суммы в целых UZS в текущей модели.
- До полного возврата legacy invoice state остаётся `paid`; в ответе
  amount refund указаны `state: partially_refunded`, `refunded_total` и
  `remaining`, а GET invoice дополнен `refunded_total`. Клиент должен
  отображать частичный возврат по этим данным. Старый полный refund
  разрешён только для счетов без частичных возвратов. Остаток возвращается
  через amount refund. Открытый спор блокирует обычные возвраты.
- Внутренний chargeback после частичного возврата исполняется на остаток
  суммы, после отдельных maker/reviewer/executor. Внешний chargeback
  карточной схемы не реализован и требует конкретных партнёрских правил.
- Миграция 007 (schema 8) добавляет неизменяемые строки amount refunds,
  валидирует проводки и суммы, обновляет финальные проверки invoice и fee,
  добавляет read-only integrity view. Старые журналы не переписываются.
  Обе копии runtime_roles.sql синхронизированы; применить администратором
  после миграции в отдельном staging. Проверить preflight и отсутствие
  прав UPDATE/DELETE на новых финансовых таблицах.

## Приёмка / границы блока 2
| Направление | Реализация до лицензии | Обязательное подтверждение |
|---|---|---|
| Ledger, hold, settle | PostgreSQL, идемпотентность, блокировки | Реальный PG CI, внешняя проверка |
| Банковские инструкции | Контракт, durable claim, sandbox rail | API/PKI/схема статусов партнёра |
| Отправка/неизвестный результат | single issue + lookup-only | fault injection реального sandbox |
| Clearing/reconciliation | Пакеты с контрольными итогами, независимый review, offline сверка | Подписанные полные выписки, cut-off и подтверждённый opening/closing |
| Fees/refunds/disputes | Внутренний полный/частичный возврат, fee reversal, остаточный chargeback | Тарифы, налоги, округление и dispute SLA партнёра |
| KYC/AML/risk | Workflow решений, блокировки и лимиты | Проверенные поставщики данных, правила AML, санкции, реальные операционные процедуры |

Не выдавать за коммерческую готовность. Для банковского sandbox понадобятся
спецификации, тестовые credentials, сопоставление реквизитов, подтверждённый
финансовый контур и тесты каждого партнёра. Окончательная приёмка включает
пентест, результаты PostgreSQL CI, бухгалтерский аудит и регуляторную проверку.

## Поставка
Только `spyderpay-core-update-v008.zip`; постоянный YAML не меняется.
Архив содержит предыдущие версии, включая 0.7.1, и обновлённые конфигурации.
Локальный тест Python и статическая проверка не заменяют SQL integration test.
