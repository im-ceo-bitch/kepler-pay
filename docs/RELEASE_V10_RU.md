# SpyderPay Core 0.10.0 — завершение доступного инженерного объёма блока 3

Накопительное обновление v010. Схема PostgreSQL остаётся 9; миграции предыдущих
версий и финансовые функции сохранены. Единственный workflow — действующий
постоянный распаковщик. Новая версия не включает YAML GitHub Actions.

## Новое
- Раздельные клиентский и служебный TLS-входы NGINX; служебный требует клиентский
  сертификат и сохраняет HMAC-проверку API. Клиентский не пропускает служебные
  маршруты и заголовки. Служебный не пропускает пользовательские bearer-токены.
  Sandbox credit недоступен через оба входа. Обе точки привязаны к loopback;
  firewall, PKI, L4 DDoS mitigation и внешний WAF — отдельные контроли.
- Подписанный мониторинг: роль `monitor` допускает только GET health/ready.
  Выход структурирован, без данных счетов и секретов. Системная служба и таймер
  готовы к установке. Реальный SIEM и доставка алертов не настроены.
- Merchant POS: CLI и настольный Tk-интерфейс. Продажа сохраняется перед запросом
  создания счёта. Повтор после сетевого сбоя использует тот же идентификатор.
  QR содержит подписанный preview-токен; он не подтверждает оплату. Статус и
  возвращённая сумма запрашиваются у финансового API. Нет NFC-дебета или
  автономного одобрения. Вход и получение токена — через внешний доверенный IdP.
- Backup manifest format 3: подписанный SHA-256 ciphertext, контрольные итоги и
  отпечатки точного содержимого всех 40 финансовых/операционных таблиц `sp_*`.
  Проверяются также последовательности двух bigserial при восстановлении.
  Резервные копии старых форматов остаются доступными для проверки, но не дают
  такой же гарантии полноты. Это логический дамп, не замена PITR.
- Исправлена диагностика отсутствующих hold-счетов и нарушения области проводок.
- Добавлен runner автоматических проверок, который не может включить реальные
  деньги или выдать сертификат готовности.

## Установка обновления
Загрузить `spyderpay-core-update-v010.zip` в корень репозитория. Никакого изменения
workflow или ручного редактирования исходников. Постоянный распаковщик проводит
unit + PostgreSQL + security проверки перед коммитом. Если CI красный, релиз
не считается принятым, требуется лог. Не отключать проверки.

## Фактическая граница готовности
Локальные тесты Python, защищённые release gates, Merchant SDK, локальная
интеграционная проверка NGINX с временной PKI и подставным backend выполнены.
Подключение к настоящему PostgreSQL, физическому NFC/SE, IdP, Vault/HSM, резервной
инфраструктуре и коммерческому банку не испытано в среде разработки. GUI требует
Tk и дисплея; реальный POS и кошелёк ещё нуждаются в интеграции и UX-проверках.

Нельзя считать блок полностью принятым, а платформу Production-ready, без
положительных результатов внешней приёмки. Полный список и порядок испытаний:
`infrastructure/operations/acceptance-v10.md`. REAL_MONEY_ENABLED остаётся false.
